# Complexity Matrix v2.1

## 核心原则

只评估“本次变更本身”的风险，不因代码所在领域、计划使用的 Agent 数量或团队规模重复加分。

- 7 个风险维度，每维 0~3 分。
- Architecture、Data、Infrastructure 权重 ×2，Runtime Risk 权重 ×3。
- Collaboration 不再计入风险总分；它在评分后形成独立的 Delivery Profile。
- 必须先按锚点评分，再应用 `routing-rules.md` 的语义红旗。

## 评分锚点

| 维度 | 权重 | 0 分 | 1 分 | 2 分 | 3 分 |
|---|---:|---|---|---|---|
| Scope | ×1 | 单点或单文件局部修改 | 同模块少量文件 | 跨模块或共享组件 | 跨服务、全局或大量消费者 |
| Business | ×1 | 不改变业务语义 | 单一规则、无状态迁移 | 多规则或有限状态迁移 | 复杂状态机、监管或强约束规则 |
| Code Impact | ×1 | 叶子逻辑、无调用方影响 | 单条可追踪调用链 | 多层调用、公共 API 或异步消费者 | 广泛调用链、事件驱动或难以穷举的消费者 |
| Architecture | ×2 | 组件边界不变 | 调整既有组件协作 | 新组件、新契约或边界显著变化 | 模块/服务边界重构或核心架构变化 |
| Data | ×2 | 无持久化变化或只读 | 兼容字段/查询变化，无迁移 | 可逆 Schema、回填或一致性变化 | 不可逆/大规模迁移、核心表重构或高风险一致性 |
| Infrastructure | ×2 | 无基础设施影响 | 服务本地配置 | 共享平台或可选横切能力 | 改变全局默认、关键平台或部署运行方式 |
| Runtime Risk | ×3 | 文案、开发期或无运行时语义 | 影响边界清晰且易回滚 | 用户可见关键流程，失败会降级服务 | 改变资金、库存、权限、敏感数据、安全或难回滚语义 |

## 总分与基础档位

总分范围：0~36。

| 总分 | baseline_tier |
|---:|---|
| 0~5 | R1 |
| 6~11 | R2 |
| 12~22 | R3 |
| 23~36 | R4 |

`baseline_tier` 只是基础档位。`final_tier` 还必须应用语义红旗；门控则在 final tier 的基础门控上继续叠加。

## Delivery Profile（不计入风险总分）

评分后独立记录：

| 字段 | 可选值 | 含义 |
|---|---|---|
| agents | 1 / 2+ | 是否存在至少两个可独立测试的执行批次 |
| worktrees | none / optional / required | 是否需要工作区隔离 |
| rollout | none / standard / coordinated | 是否需要跨服务协调发布 |
| ownership | single / multi-team | 是否跨团队或跨所有者 |

多 Agent、worktree 和跨团队协作只增加隔离、集成与发布门控，不自动把业务风险升为 R4。

## 评分纪律

1. 每一分都要引用代码库证据或明确需求事实。
2. 同一事实不得在多个维度重复放大；例如“跨服务”主要计 Scope，只有边界本身变化时才同时提高 Architecture。
3. 仅修改高风险目录中的文案，不等于改变高风险业务语义。
4. 探索后证据变化时重新评分，并记录旧值、新值和原因。
5. 使用 `calibration-cases.json` 的基准案例校准判断。
